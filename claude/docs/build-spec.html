Build specification

Registration intake: accept now, resolve identity afterwards

Lumen Health case study. The one component of the target architecture specified here in full: the path that takes a kit registration from the member portal, accepts it immediately and hands identity resolution to a background process.

A developer or a coding agent should be able to build it from this page without asking questions. Where the page makes an assumption it says so and the last section lists them.

Summary

Today register_kit resolves a CRM account inside the customer's request. It can raise IdentityConflict (legacy-sync/legacy_sync/registration/register.py:32), RegistrationBlocked (register.py:43, from the duplicate rule at crm/client.py:40) and InactiveOwner (crm/client.py:60, reached through the gift move at register.py:45-46). Each one fails a customer's registration for a reason the customer cannot see or fix.

The replacement has two halves with a durable hand-off between them. The portal validates the form, writes the registration and an outbox event in one local database transaction and answers. A relay then delivers the event to the identity service at least once. The identity service creates a provisional person at once, resolves it against existing people and tells the portal the outcome. The portal owns the event until the identity service has stored it, so a registration cannot be lost between the two.

One transactionthe registration and its outbox event commit together or not at all
Four rejectionsthe only reasons the portal refuses a registration, all about the form or the kit
Ten attemptsover about fourteen hours before an event is parked, never deleted
Two keysregistration_id and kit_barcode make every repeat harmless
Nightly proofa reconciliation job compares portal and identity records and repairs gaps
Zero CRM callsnothing on the customer path or in the handler touches the CRM

Production transport and vendor capabilities are assumptions in this document, not known facts. The supplied repository is a local CSV replay with an in-memory CRM stand-in, so it shows the behaviour being replaced and says nothing about queues, databases or the real CRM's API. The contract below is written so that the transport can change without changing the behaviour.

Scope, non-goals and glossary

In scope

  • The portal's registration endpoint and what it validates.
  • The portal tables for registrations and the outbox and the relay that drains the outbox.
  • The registration.accepted event and the identity.registration_resolved event that returns the outcome.
  • The identity service's ingest endpoint, inbox and handler for this one event type.
  • The registration state machine, outage behaviour, replay, nightly reconciliation, metrics and alerts.
  • The feature flag and backout for this component.

Non-goals

  • The matcher's field weights and calibration. The handler calls the matcher with the thresholds from the target architecture and treats its score as an input.
  • The review screen. This page defines the review item the handler creates, not the screen that works it.
  • Order events from e-commerce, EHR chart creation and the lab flow. They continue as today and do not wait for identity.
  • Editing a registration after it is accepted. Corrections go through support and arrive as separate events.
  • The CRM sync internals. This page fixes only the rule that it is asynchronous and cannot affect a registration.

Acceptance boundary

The portal accepts a registration if and only if the checks in the first table pass. They read only the portal's own database and the request. Nothing else can reject a registration.

Transactional outbox

The registration row and its outbox row are inserted in one local transaction in the portal's own database. If the transaction commits, both exist. If it fails, neither does and the customer gets the portal's own 503. There is no second system in the transaction, which is the whole point: the identity service being down cannot make the commit fail.

From the commit onward the portal owns the event. It stays the owner until the identity service acknowledges it and ownership comes back to the portal if a dead letter is replayed. The identity service owns it from the acknowledgement onward and must have stored it durably before it answers.

The write path

BEGIN;
  -- 1. the kit must exist; the unique constraint on registration.kit_barcode decides the race
  INSERT INTO registration (registration_id, kit_barcode, client_request_id, state,
                            first_name_enc, last_name_enc, email_enc, email_hash,
                            phone_enc, birthdate_enc, payload_hash)
  VALUES ('R' || lpad(nextval('registration_seq')::text, 6, '0'), $kit, $key, 'accepted',
          $fn, $ln, $em, $emh, $ph, $dob, $hash)
  RETURNING registration_id;

  -- 2. the event, built from the same values, in the same transaction
  INSERT INTO registration_outbox (event_id, registration_id, event_type, schema_version,
                                   payload_enc, status)
  VALUES (gen_random_uuid(), $registration_id, 'registration.accepted', '1.0', $payload, 'pending');
COMMIT;
-- 3. after commit only: NOTIFY the relay so the first attempt happens within a second.
--    A lost notification costs at most one poll interval (1 second).

Nothing is sent to the identity service inside the transaction or in the request thread. The notification in step 3 is an optimisation. If it is lost the relay's one-second poll picks the row up.

The return event

When the handler finishes, the identity service sends identity.registration_resolved to the portal. It carries no personal data.

{
  "event_id": "c41e8a07-92b3-4d56-b0f1-7a6e3d2c9b48",
  "event_type": "identity.registration_resolved",
  "schema_version": "1.0",
  "registration_id": "R000424",
  "person_key": "p_7Kq2Xw9mTa",
  "outcome": "merged",
  "resolution_seq": 1,
  "reason_codes": ["email_exact", "birthdate_match", "name_match"],
  "resolved_at": "2026-11-09T14:03:29Z"
}

outcome is one of merged, new or review. resolution_seq starts at 1 for each registration and rises by one on every later change, such as a review decision or a split.

Versioning rule

  • The version is major.minor in the body and is also sent as the message attribute schema-version so a consumer can route before parsing.
  • A minor change only adds optional fields. Each published version of the schema is closed, so a producer raises the minor version whenever it adds a field. A consumer that receives a higher minor than it knows strips the fields it does not recognise, then validates against the highest minor it knows within the same major.
  • A major change removes or retypes a field or changes its meaning. The producer then sends both versions for at least 90 days, rendering each body from the same outbox row and every consumer must accept the current major and the one before it.
  • An event the consumer cannot validate is answered with 422 and a reason code. It is never silently dropped.

Idempotency

The key is registration_id. The kit barcode is a second unique key on the portal side. Everything on this page is built so that doing any step twice leaves the same result as doing it once.

Comparing email_hash values is a string comparison inside the portal. It is not identity resolution and it calls nothing.

Delivery-side repeats

  • The relay can send the same event many times: after a timeout whose request actually succeeded, after a lease expiry, after a replay. Each send carries the same event_id.
  • The identity service inserts into inbox_event with event_id as primary key and registration_id unique. A conflict on event_id returns 200 duplicate without reprocessing.
  • A different event_id for a known registration_id with the same payload_hash is treated as a duplicate as well (200 duplicate).
  • A known registration_id with a different payload_hash is a producer bug, since an accepted registration is immutable. The service answers 409 registration_payload_mismatch, stores nothing and raises an alert. The relay does not retry a 409.
  • The handler's own steps are idempotent too: the provisional person is keyed by the portal source_record (system = 'portal', record_id = registration_id), so a handler that crashes and reruns finds the person it already created.

Return-event repeats

The portal applies a resolution only if its resolution_seq is higher than the stored one. A repeat or an out-of-order older event changes nothing.

Delivery

Delivery is at least once. The relay is a small process in the portal's deployment, running as two or more instances over the same table.

Relay behaviour

  • It claims up to 50 rows at a time with SELECT ... WHERE status = 'pending' AND next_attempt_at <= now() ORDER BY next_attempt_at FOR UPDATE SKIP LOCKED, sets status = 'in_flight' and a 30-second lease, then sends them.
  • Claiming a row is what counts as an attempt: the claim increments attempts and sets the lease in the same statement, before anything is sent. A row whose lease expires without a result returns to pending with its attempt already counted, so a relay that keeps crashing or losing responses still reaches the ten-attempt limit and the row goes to dead. The send may have succeeded, which the identity service's idempotency absorbs. Expiries are also counted in lease_expiries. Three on one row raise an alert, because repeated expiry points at the relay and not at the event.
  • It polls every second and also wakes on the notification after commit.
  • Each send has a connect timeout of 2 seconds and a total timeout of 5 seconds.

Circuit breaker

If 5 consecutive attempts across any events fail with a timeout or a 5xx, the breaker opens. While it is open the relay claims nothing except one probe event every 30 seconds. A probe is exempt from the attempt count, so the breaker does not increment attempts on any row and does not push next_attempt_at further out. When a probe succeeds the breaker closes and the backlog drains at up to 50 events per second. This keeps a long outage from sending thousands of healthy events to the dead letter state.

Ordering

  • Not needed between registrations. Two registrations can be delivered and resolved in any order. The handler's locking (see below) handles the case where they concern the same person.
  • Not needed within a registration for the accepted event, since there is exactly one per registration.
  • Needed on the return path only as a sequence number: resolution_seq per registration, applied only when higher.

Dead-letter queue

The dead letter queue is the set of outbox rows with status = 'dead', exposed by a view. Nothing is moved or deleted, so the registration, its payload and its history stay in one place. A dead row keeps last_error_code, attempts and the time it died. Dead rows are never scrubbed. The portal registration state becomes dead_lettered.

Identity service handler

The ingest endpoint and the handler are separate. The endpoint's only job is to store the event and answer. The handler runs afterwards from the inbox with its own retries. That split is what lets the service acknowledge quickly and keeps a slow matcher from causing timeouts at the relay.

Ingest

  1. Authenticate the caller and check the scope events:write.
  2. Validate the body against the schema for its schema_version. On failure answer 422.
  3. Apply the duplicate rules from the idempotency section.
  4. Insert the row into inbox_event and commit.
  5. Answer 202. The answer is sent only after the commit. If the commit fails the service answers 503 so the portal keeps ownership.

Handler, in this order

  1. Take the next unhandled inbox row. Take advisory locks on every blocking key the matcher uses for this registration: the hashed normalised email, the hashed normalised phone and the hash of surname plus birthdate, in sorted order. Any two registrations that could be candidates for each other share at least one of these keys, so they cannot match in parallel and both end up as new people. Household evidence is not a blocking key in this handler. Locks are a first defence only. A sweep runs every 15 minutes over provisional people created in the last hour and scores each against the others with the same matcher, so a duplicate that slipped through is merged or sent to review by the same rules. The nightly reconciliation repeats the sweep over the whole day.
  2. Create the provisional person with provisional = true and status = 'active' if the portal source_record for this registration_id does not exist. Add its identifiers (name, email, phone, birthdate) with source_system = 'member_portal' and observed_at from the event. Create the source_record with confidence 1.0, method rule and evidence {"basis": "registration_created"}.
  3. Upsert the kit_role row for the kit barcode: set registrant_person to the provisional person and stage to registered. Stage never moves backwards: if the row already says resulted it stays there. If the order event has not arrived yet, create the row with the buyer empty. The order event fills it later.
  4. Commit steps 2 and 3. From here the kit has a registrant whatever happens next, even if matching fails or is delayed.
  5. Run the matcher for the provisional person against all other active persons. Exclude the provisional person itself. Apply the birthdate veto: where both birthdates are known and different, the candidate is dropped. A birthdate equal to the placeholder 1920-01-01 (legacy-sync/legacy_sync/config.py:15) counts as unknown, not as a value to compare.
  6. Take the best-scoring remaining candidate and decide:
    • Score 0.90 or above and no second candidate at 0.90 or above: merge the provisional person into the candidate. Repoint the portal source_record, set merged_into on the provisional person, move kit_role.registrant_person to the survivor, apply the strictest consent and write one identity_event of type merge with the actor system:matcher, the score and the reason codes. If the merge would break a clustering constraint from the target architecture (two birthdates in one person, two EHR charts), create a review item instead.
    • Score 0.90 or above for two or more candidates: do not merge. Create one review item per candidate with the reason code multiple_strong_candidates and keep the provisional person.
    • Score from 0.60 up to but not including 0.90: create a review_item naming the portal source_record and the candidate's best record, with the score and reason codes and no names. Keep the provisional person as it is.
    • Score below 0.60 or no candidate: set provisional = false. The provisional person is now a new person.
  7. Write the registration_resolution row (outcome, person_key, score, reason codes, resolution_seq 1) in the same transaction as the decision.
  8. Write the outgoing identity.registration_resolved event and the CRM and marketing sync tasks to the identity service's own outbox in that same transaction.
  9. Mark the inbox row handled and release the locks.

Rules the handler never breaks

  • It never checks CRM account ownership, never reads a CRM owner field and never calls the CRM. The identity store and the matcher are its only inputs.
  • It never fails an event for a matching reason. A matcher error is retried on the handler's own schedule (10 seconds, 1 minute, 5 minutes, 30 minutes, then every 2 hours up to 20 attempts). Meanwhile the kit already has its provisional registrant from step 4, so nothing the customer sees is waiting.
  • It never moves a purchase between accounts. It writes roles.
  • It never deletes a person. A merge sets merged_into and is reversible by a split.

The state lives on the portal's registration row. It is a projection for operators and for the portal's own screens. The identity service remains the authority on who a person is. The state tells you where the hand-off stands.

Interface to human review

This component hands uncertain matches to human review and takes the answer back. The review workflow itself, its queue, screens, service levels and safeguards, is a separate component described under human review in the target architecture. What follows is the contract between the two, which is everything a builder of registration intake needs.

What this component guarantees to review

  • A registration whose best candidate scores from 0.60 up to but not including 0.90, or scores higher but is blocked by a cluster rule or an unmeasured rule, produces exactly one review_item per pair of persons. A second registration raising the same question attaches its record pair to the open item instead of opening another.
  • The item is written in the same transaction as the provisional person and the kit_role row, so an item never refers to a person that does not exist.
  • The item carries person keys, record IDs, score, reason codes and an evidence_version: a hash of the identifier and link rows the matcher read. It carries no names, birthdates or contact details.
  • Priority is set here: 1 when either person has a result, 2 when the kit belongs to a gift order, 3 otherwise.

What happens to the registration while the item is open

  • The registration is in state in_review. To the customer it is identical to a resolved one: the kit is registered, the chart and lab flow continue and results are shown to the registrant.
  • The provisional person is a full person. Its key is sent to the portal, the EHR and the CRM in the normal way and remains valid whatever the reviewer decides.
  • identity.registration_resolved is emitted with resolution = "in_review", so consumers know the key may later merge into another.
  • No timer moves a registration out of in_review. Only a decision or new evidence does.

Acceptance tests for this interface

  1. Given a registration in in_review, when a same decision arrives with a matching evidence_version, then the provisional person merges, the registration is resolved_merged and one identity_event of kind merge exists.
  2. Given the same item, when a new order event adds an email to either person before the decision, then the decision is answered 409 evidence_changed and no merge happens.
  3. Given two registrations that raise the same question, then one open review_item exists with two supporting record pairs.
  4. Given an item open for 30 days with no decision, then the registration is still in_review, the customer can see results and no merge has happened.
  5. Given a different decision, when the matcher later scores the same pair with unchanged evidence, then no new item opens.
  6. Given a same decision delivered twice, then exactly one merge event exists.
  7. Given a same decision that would join two persons with different known birthdates, then the answer is 422 constraint_violation and both persons are unchanged.

Outage behaviour, replay and reconciliation

Identity service down for minutes

The portal keeps accepting. Every row is committed with its outbox event. The relay retries on the schedule, usually succeeding on attempt 2 to 4 once the service is back. Customers notice nothing. The only visible effects are a delayed person_key on the registration and a delayed CRM and marketing update.

Identity service down for days

The breaker opens after 5 consecutive failures, usually within a minute. From then on events accumulate as pending without using up their attempts. The portal database grows by one small row per registration, which at the volume in the sample data is trivial. The oldest-pending alert pages within 15 minutes. When the service returns, a probe closes the breaker and the backlog drains at up to 50 events per second.

If the outage began before the breaker was introduced or the breaker was disabled, rows that reach 10 attempts become dead. That is safe, because nothing is deleted and the replay procedure below recovers them.

Identity store unavailable after the portal has accepted

The ingest endpoint cannot commit to inbox_event, so it answers 503 and does not acknowledge. The portal therefore still owns the event and keeps retrying. The identity service never reports an event as received before the inbox commit. If the store fails after the inbox commit but before the handler finishes, the handler retries from the inbox on its own schedule and the nightly reconciliation catches anything that is still missing. In none of these cases is the customer's registration affected, because the portal's row was committed first and sits in a database the identity store does not share.

Replay procedure

  1. Confirm the cause is fixed. Check the identity service health endpoint and send one synthetic registration.accepted event for a test kit. It must come back 202 and then 200 duplicate on a second send.
  2. Count what is waiting: GET /internal/v1/outbox/stats returns counts by status and by last_error_code.
  3. Run the replay as a dry run: POST /internal/v1/outbox/replay with {"status": "dead", "since": "...", "dry_run": true}. It returns the registration IDs it would requeue and no personal data.
  4. For rows that died with schema_invalid, deploy the producer fix first and add "rebuild_payload": true. The payload is regenerated from the registration row with the same event_id.
  5. Run it for real with "rate_limit_per_second": 20 and "batch_size": 500. Each row goes back to pending with attempts = 0 and replay_count plus one. The state returns to event_pending.
  6. Watch portal_outbox_pending_total and identity_inbox_to_resolution_seconds. Raise the rate to 50 per second only if both stay flat.
  7. Run the reconciliation job by hand (below). It must report zero gaps.
  8. Record the replay in the operations log: who, why, how many, the time range and the reconciliation result.

Replay is safe to repeat, because the same event_id and registration_id make the identity service answer 200 duplicate for anything it already holds.

Nightly reconciliation

A scheduled job runs at 02:00 local time. It compares the portal's registrations with the identity service's portal source_record rows for a window that starts 36 hours before the run and ends 15 minutes before it, so events still in flight are not counted.

  1. The job pages through GET /internal/v1/registrations/ids on the portal, which returns registration_id, kit_barcode, payload_hash and state and nothing personal.
  2. It asks the identity service for the matching registration_resolution and inbox_event data through GET /v1/registrations/{registration_id}/resolution in batches of 200.
  3. It classifies each difference.
GapMeaningAction
missing_in_identityThe portal has the registration and the identity service has no inbox rowRequeue the outbox row with the same event_id (a replay with reason recon). Count it
unresolved_after_24hIn the inbox for over 24 hours with no resolutionOpen a ticket and re-run the handler for that inbox row
state_staleThe identity service has a resolution that the portal row does not showResend the identity.registration_resolved event
hash_mismatchBoth have the registration but the payload_hash values differNo automatic fix. Page. This should be impossible

If the number of automatic repairs in one run exceeds 1,000 or 5 percent of the window, the job repairs nothing further and pages, since that shape means a systemic fault rather than stray losses. The job reports its counts as metrics every run, including zero.

Downstream effects

CRM

The identity service writes to the CRM only from its own outbox, after the handler has committed. The CRM task carries person_key, the registration ID and the preferred contact details. It has its own retry schedule and dead-letter handling. A CRM failure, a duplicate-rule hit or an inactive owner marks the task failed and raises a CRM sync alert. It never changes the registration's state or the identity result and it never reaches the customer.

The duplicate rule is set to alert, as in the target architecture, so a CRM-side duplicate becomes a signal for the matcher and not a gate.

Gift orders

The legacy code moves the opportunity to the registrant's account for a gift (register.py:45-46) and fails when the new owner is inactive (crm/client.py:57-60). The new handler never moves a purchase. The buyer comes from the order event and stays on the opportunity. The recipient is recorded as kit_role.registrant_person. The CRM task writes the recipient as a role field on the opportunity for sales and support to read. If the buyer and the registrant resolve to the same person, the role simply has the same person in both places.

Marketing

The stage that marketing receives comes from kit_role.stage and not from a CRM account. Setting it to registered in step 3 of the handler is what stops the "please register" message for that kit. The stage feed is batched every 15 minutes and carries person_key, kit barcode, stage and channel consent only.

Chart and lab

The portal's existing chart and lab flow runs on the registration row. It does not wait for the resolution event.

Duplicates

  1. Same kit twice, same person. Given R000424 exists for KT0000481 and jane.example@example.com. When the same email submits KT0000481 again with a new idempotency key. Then the response is 200 with registration_id R000424, no new row and no new event.
  2. Double click. Given two requests with the same Idempotency-Key sent 50 ms apart. Then exactly one row and one event exist and both responses name the same registration.
  3. Same kit, different person. Given R000424 exists. When sam.sample@example.com submits KT0000481. Then the response is 409 kit_already_registered, no row is created and a support case is opened.
  4. Simultaneous submissions. Given two different emails submit KT0000481 within the same millisecond. Then exactly one gets 201 and the other gets 409.
  5. Duplicate delivery. Given the relay sends the same event three times. Then the identity service creates one provisional person, one source_record and one resolution and the second and third answers are 200 duplicate.
  6. Payload mismatch. Given an event with a known registration_id and a different payload_hash. Then the answer is 409, nothing is changed and an alert fires.

Delivery and outages

  1. Identity service down. Given the ingest endpoint returns 503 for 20 minutes. When 40 registrations arrive. Then all 40 are accepted, none is dead, attempts follow the schedule or the breaker holds them and after recovery all 40 are delivered and resolved.
  2. Long outage. Given the endpoint is down for 3 days with the breaker working. Then no row is dead, the oldest-pending alert fired within 15 minutes of the first failure and the backlog drains at the configured rate on recovery.
  3. Poison event. Given a payload that fails validation. Then it answers 422, the row is dead at once, the state is dead_lettered and other events continue.
  4. Lost acknowledgement. Given the identity service stores an event but the response never arrives. Then the relay retries, the answer is 200 duplicate and the row ends delivered.
  5. Identity store unavailable after acceptance. Given the portal has accepted R000425 and the identity store rejects the inbox write. Then the endpoint answers 503, the outbox row stays pending and the portal still owns it.
  6. Crash between ingest and handler. Given the service restarts after the inbox commit. Then the handler picks up the inbox row and completes it once.
  7. Replay. Given 12 dead rows and a working service. When an operator runs the replay with a rate of 20 per second. Then all 12 end delivered, replay_count is 1 and the reconciliation reports zero gaps.
  8. Reconciliation. Given a registration present in the portal and absent from the identity service. When the nightly job runs. Then it requeues the event with the same event_id and reports one missing_in_identity.
  9. Reconciliation limit. Given 2,000 gaps in one run. Then the job repairs none beyond the threshold and pages.

Handler

  1. Given no existing person. Then a provisional person is created with confidence 1.0, kit_role.registrant_person is set, the stage is registered and the outcome is new.
  2. Given a candidate scoring 0.95 with matching birthdates. Then the provisional person is merged into it, one merge identity event is logged and the outcome is merged.
  3. Given a candidate scoring exactly 0.90. Then it merges. Given a candidate scoring exactly 0.60. Then a review item is created.
  4. Given a candidate scoring 0.75. Then a review item is created, the provisional person remains and kit_role.registrant_person still points to it.
  5. Given a candidate scoring 0.45. Then provisional becomes false and the outcome is new.
  6. Given a candidate with a high score whose birthdate differs from the registrant's. Then the candidate is dropped by the veto and no merge happens.
  7. Given two candidates both scoring 0.93. Then there is no merge and two review items carry multiple_strong_candidates.
  8. Given a kit whose stage is already resulted. When the registration is handled. Then the stage stays resulted.
  9. Given a gift order where buyer and registrant differ. Then the opportunity remains on the buyer and the recipient is recorded as registrant.
  10. Given the CRM write task fails 5 times. Then the registration state, the identity result and the customer's view are unchanged.
  11. Given two registrations from the same email arriving together. Then they are matched one after the other and end up as one person, not two.

Privacy

  1. Given a full run of tests 1 to 35 with logging captured. Then no log line, metric label or error body contains any name, email, phone or birthdate used in the test data.

Rollout flag and backout

Flag

The portal reads registration_intake_mode on every request. The last known value is cached for 60 seconds. If the flag service cannot be read and there is no cached value, the mode is off.

ModeCustomer pathIdentity effect
offThe legacy register_kit path, unchangedNone
shadowThe legacy path decides the customer's answer. After it succeeds the portal also writes the registration and outbox rowsThe identity service processes the events with CRM and marketing tasks switched off. Its decisions are compared with what the legacy path did
onThe new acceptance path. No CRM call in the requestFull, including the CRM and marketing tasks

The ramp for on uses a percentage of kit barcodes by hash: 1, 10, 50, then 100 percent, with at least a day at each step. A given kit always takes the same path. The step moves on only if the targets in the observability section hold.

The first change to ship is the decoupling: the mode on with the identity service only storing and resolving events. That removes the blocking behaviour from the customer path. Systems consuming the resulting person_key follow in later phases of the rollout plan.

Backout

  1. Pause the relay. A kill switch stops the sends and leaves the outbox filling. Customers are unaffected. Use this first for any fault on the identity side.
  2. Drop the percentage or set the mode to shadow. Use this when the fault is on the acceptance path itself.
  3. Set the mode to off as a last resort. New registrations go back to the legacy path, which brings the old blocking failures back, so this is a regression of the fixed constraint and needs a named approver.

Whatever step is taken, rows already accepted stay in place and the relay keeps owning them. The tables are never dropped during a backout. Registrations accepted under on are not in the legacy CRM sync, so their CRM updates come from the identity service's tasks and those must keep running or be run by hand from the outbox once the fault is fixed.

Back out when any of these holds:

  • The acceptance error rate is above 1 percent over 5 minutes.
  • Acceptance p99 is above 1 second for 15 minutes.
  • The reconciliation job finds a registration missing after its repair.
  • The oldest pending row is older than 60 minutes while the identity service is healthy.
