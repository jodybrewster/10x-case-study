01 · Scope

What this code does today

The replay loads CSVs into memory, initializes the CRM stand-in with older accounts, processes e-commerce orders in creation-time order, creates an opportunity for each order, then processes portal registrations. It prints outcome counts. It does not call a live CRM or implement an end-to-end identity registry.

Reading the evidence: the sync has multiple ways to associate records, but it does not record why an account match was made. The address fallback can therefore turn a household resemblance into a person-level CRM link without leaving an auditable matching decision.

Sources: replay.py:15-50, store.py:5-16.

05 · E-commerce to CRM

Order sync and account selection

For each order, the resolver tries an e-commerce customer ID, then the order email, then a last-name-and-ZIP address lookup. If all fail, it creates an account. The replay then creates an opportunity linked to the selected account.

The account lookup for an existing e-commerce ID takes the first result. Email lookup can return primary or secondary email matches. The address lookup compares only last name and ZIP, then the order resolver also takes the first result. The function’s docstring says strict email matching, but the configured address fallback is active.

Sources: order_sync.py:6-26, 29-43, config.py:3-12, client.py:24-35, 48-55.

06 · Portal, kit and CRM

Registration, duplicate checks and gift handling

A registration is joined to a kit and its order. The code looks up a CRM account using the registrant’s email, checks name and date of birth, creates an account if needed, then moves a gift opportunity to the matched registrant account.

The replay records registration outcomes for duplicate-rule blocks, identity conflicts and inactive owners. Registration handling is synchronous in this sample: account resolution happens before the registration is counted as accepted.

Sources: replay.py:36-45, client.py:37-45, 57-61.

08 · Findings

Six reported symptoms

“Confirmed” means the code contains a direct behavior that can produce the symptom. “Partial” identifies a concrete failure path without proving it explains every reported case. “Not proven” means the relevant production path or data transformation is absent from the supplied code.

1
Confirmed cause

Orders land on a family member’s account

If customer-ID and email lookups fail, address fallback searches by shipping last name and ZIP. The order resolver selects the first match, with no uniqueness or person-level check. A household address can therefore attach the purchase to a relative’s CRM account.

Direct path: fallback enabled → last name + ZIP lookup → first result selected.

order_sync.py:12-24config.py:3-5client.py:32-35
2
Confirmed cause

CRM email changes after an order

After resolving or creating an account, every order calls update_contact_details with the order email. The CRM stand-in writes that value directly to primary_email. If the chosen account belongs to another household member, their primary email can be replaced by the buyer’s order email.

Direct path: account match → order email written as primary email, even when it differs from the CRM value.

order_sync.py:29-43client.py:48-55
3
Confirmed cause

Registration is rejected as a possible duplicate

When the registration email has no CRM match, the flow creates an account using the registrant’s name and the order’s shipping ZIP. The duplicate rule blocks account creation when first name, last name and ZIP match an existing account. That exception becomes RegistrationBlocked, which the replay counts as a rejected registration.

Direct path: no email match → create registrant account → exact first/last/ZIP collision → block.

register.py:28-43config.py:7-12duplicate_rules.py:4-11
4
Specific failure path

Gift registrations or purchase moves fail

The gift path tries to move the opportunity to the account found for the registrant. The CRM stand-in raises InactiveOwner when that destination account has an inactive owner, and the replay counts this as a registration failure. The flow can also fail earlier on a duplicate block or identity conflict. The code does not show a support workflow or prove which path explains every reported gift failure.

Direct path: gift → move opportunity to registrant account → inactive destination owner → exception.

register.py:22-48client.py:57-61replay.py:36-45
5
Not established by supplied code

Marketing asks people to register after results are ready

The stage helper checks results before registrations, so it returns results_ready when given a truthy results collection keyed to that CRM account. The replay does not load lab results or construct results_by_account. The likely fault is upstream: results may not be linked to the account key used by the marketing stage calculation, or a separate sender may use stale state. Confirm against that missing mapping and sender before naming a root cause.

Evidence limit: correct precedence is present; result-to-account mapping and campaign send path are absent.

stage.py:6-14replay.py:15-50
6
Confirmed cause

Text opt-out is lost when accounts merge

The merge removes the losing account and copies selected identity/contact fields, but the merge field list omits sms_opt_out and do_not_call. If the losing account carries an opt-out and the survivor does not, that preference disappears with the removed record. The merge also has no consent history or rule to preserve the more restrictive state.

Direct path: loser with opt-out removed → consent fields not copied or reconciled.

10 · Architect notes

Additional findings that affect the design

Link keys are referentially completeAll order-to-customer, order-to-kit, opportunity-to-order, registration-to-kit and result-to-kit/chart references found in the CSVs resolve to a row in the referenced table.
Referential integrity is not person identityThere are 30 gift orders, yet the CRM opportunity gift-recipient field is blank on all 905 opportunity rows. Preserve buyer, recipient, registrant and patient as separate roles.
The snapshot is mid-lifecycleThere are 547 test-kit orders and 547 kit rows, 433 registrations and 406 results. All 406 result kits have registrations; 27 registered kits have no result row yet. That can reflect timing, not necessarily a broken join.

Matching fields are not unique person keys

Across CRM accounts, 58 normalized primary-email values appear on 116 records. Portal registrations contain 78 repeated email groups covering 170 records. The CRM duplicate-rule tuple (first name, last name, ZIP) occurs in 87 groups covering 181 accounts. These are collision counts, not proof of which rows are duplicate people.

Source: config.py:11-12; counts derived from supplied CSVs.

The CRM e-commerce crosswalk itself has collisions

Of 689 CRM accounts, 520 have an e-commerce customer ID, but only 518 distinct IDs occur. Two IDs appear on more than one CRM account. The current ID lookup returns the first match, so even its strongest lookup is not guaranteed unique in this snapshot.

Source: client.py:24-25; counts derived from crm_accounts.csv.

The matcher is present but unused

matcher_v1.py weights name, email, phone and DOB and sets a 0.75 threshold, but no active replay or sync module imports it. It also treats two missing email or phone values as a match because both normalize to an empty string. With identical names and both email and phone missing, the score reaches 0.8. Missing data must contribute no match evidence.

Source: matcher_v1.py.

Consent and timestamps need explicit semantics

CRM accounts contain 101 DOB placeholders and 140 blank DOB values. Order, account, registration and result timestamps have no timezone offsets. The prototype should treat placeholders as missing evidence; the production design should define timezone, event time and processing time.

Sources: config.py:14-15; counts derived from supplied CSVs.

Results are many-to-one by chart

The 406 lab-result rows reference 323 distinct EHR charts. Seventy charts have multiple results, with up to four results per chart. A person can have several result events; the identity or lifecycle model must not assume one result per patient.

Counts derived from lab_results.csv.
